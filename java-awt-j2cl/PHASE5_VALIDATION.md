## API completeness result

The OpenJDK inventory contains 325 top-level types and 5,014 declared members. WebAWT currently emits 150 top-level types and 2,828 declarations. After inheritance and unavailable or excluded signatures are accounted for, 2,888 of 4,757 in-scope reference members are callable.

The important release assertion is narrower and enforceable: every type and member marked implemented exists in the emitted API, with compatible type kind, extensibility, inheritance, and call signature. The gate fails when that assertion becomes false. Partial and not-started APIs remain visible in the generated report rather than being represented as complete.

The current actionable partial-type queue is led by `Component`, `Window`, `Container`, `Font`, `Graphics`, `FontMetrics`, and `Graphics2D`. The generated `compatibility/webawt-api-validation.md` is the authoritative detailed queue.

## Behavior validation model

- Dependency-free scenarios compile against OpenJDK on the JVM and against WebAWT under J2CL. This compares constructors, values, mutations, exceptions, event behavior, layouts, geometry, raster data, and image semantics from the same test vectors.
- J2CL-specific tests exercise Elemental2 DOM peers, Canvas rendering, event scheduling, controls, focus, lifecycle, and optimized Closure output.
- Playwright drives real Chromium, Firefox, and WebKit input and verifies selection, keyboard activation, native roles and focus traversal, Canvas pixels, high-DPI backing storage, and repeated DOM disposal/remounting.
- API inventory tests inspect the actual J2CL jars rather than trusting source presence or planning metadata.

## Known validation boundaries

- API presence does not prove semantic equivalence. Each newly implemented member still needs a JVM differential scenario or a browser-specific contract test before its manifest state can become implemented.
- Clipboard requires secure-context permission and user activation and is not covered by the current headless browser suite.
- Browser image loading, raster text, native font metrics, font loading, menus, scrolling controls, and several desktop-oriented APIs remain partial or not started.
- Blocking desktop event-loop behavior cannot be preserved on the browser main thread. Such members must remain explicitly unavailable or receive a documented asynchronous web mapping.
- Drag-and-drop remains deferred until its asynchronous and event-lifetime contract is approved.

## Hardening progress

The first browser-quality and release-engineering slice is implemented. Dependency drift, accidental main-source test dependencies, missing lock checksums, optimized bundle growth, cross-browser regressions, focus-order regressions, high-DPI regressions, and lifecycle leaks now have executable gates. The local validator and Linux CI run the same core checks.

The remaining hardening decisions are deliberately separate because they require product or infrastructure choices: select a real downstream application for acceptance, choose the first rendering/font golden baselines and tolerances, configure a SonarQube service and credentials, select a source-map-aware J2CL coverage mechanism, and approve a release license/SBOM policy.

## Remaining hardening options

### Option A: compatibility-first

Close the actionable partial API queue and add a behavior test for every promoted member. This is the strongest route for existing AWT source compatibility.

### Option B: rendering-first

Prioritize image drawing and loading, `ImageData` transfer, native text metrics and font loading, rendering hints, and visual golden tests with browser-specific pixel tolerances.

### Option C: browser-quality-first

Expand the passing Playwright matrix beyond its current focus, accessibility, high-DPI, and lifecycle checks with wheel input, resize observation, clipboard permission, longer lifecycle stress, and approved drag-and-drop scenarios.

### Option D: release-engineering-first

Build on the new Linux CI, dependency policy, bundle budgets, and API gate by configuring SonarQube, source-map-aware coverage, immutable release versioning, license reports, and a selected SBOM format.

## Objective

WebAWT will provide a web-based implementation of the useful `java.awt` surface for J2CL applications, backed by Elemental2 and native browser APIs.

Every API shipped in the stock-J2CL profile must either behave compatibly or have a meaningful documented browser mapping. APIs without an honest browser implementation will be omitted and recorded in the compatibility manifest rather than supplied as misleading stubs.

File dialogs and printing are explicitly outside the project scope. This excludes `FileDialog`, `PrintJob`, `PrintGraphics`, `JobAttributes`, `PageAttributes`, and the complete `java.awt.print` package.

## Feasibility constraints

J2CL does not include AWT or Swing and intentionally supplies only a partial JRE. A new, currently unclaimed package such as `java.awt` is expected to be possible as a J2CL library, but this must be proven before wider implementation.

Complete AWT signatures cannot be implemented using only the stock J2CL JRE because portions of AWT expose unavailable classes in J2CL-owned packages, including `java.io.File` and `java.lang.reflect.InvocationTargetException`, while other areas depend on absent `java.net`, `java.text`, desktop, class-loading, reflection, and threading facilities.

The initial product is therefore a documented stock-J2CL compatibility profile. A patched-J2CL profile is deferred unless complete signatures later become more important than the stock-JRE constraint.

The initial API baseline is the Java 8-era core AWT surface. A Java 17 compatibility inventory will track later APIs and prevent accidental ambiguity about the target contract.

## Compatibility categories

| Area | Implementation | Expected compatibility |
| --- | --- | --- |
| Geometry and value types | Pure Java | High; verify differentially against OpenJDK |
| Colors, shapes, paths and transforms | Pure Java with browser conversion at the backend boundary | High for common behavior; complex area and stroke algorithms require dedicated work |
| Events, listeners and adapters | Pure Java event model translated to and from DOM events | High for ordinary events |
| Component state and layout managers | Pure Java model with calculated bounds applied through peers | High, with browser-dependent preferred sizes |
| Standard controls and containers | Semantic DOM elements managed by Elemental2 peers | Medium to high; native browser appearance and metrics differ |
| Custom painting and `Graphics2D` | HTML Canvas 2D | Good for paths, transforms, clipping, strokes, gradients, text and images |
| Images and `BufferedImage` | `ImageData`, typed arrays, `ImageBitmap`, and offscreen canvas | Partial; begin with an ARGB-focused subset |
| Fonts and metrics | CSS fonts, `FontFace`, `document.fonts`, and canvas text metrics | Partial; JVM metrics, glyph outlines and shaping will differ |
| Clipboard and drag-and-drop | Clipboard events, asynchronous Clipboard API, and `DataTransfer` | Partial and subject to user activation, permissions and event lifetime |
| `Frame`, `Window`, and `Dialog` | Managed in-page layers and semantic dialog elements | Web mapping rather than native operating-system windows |
| `EventQueue.invokeLater` | Browser task queue | Supported |
| Blocking event loops, `invokeAndWait`, and `SecondaryLoop` | No safe browser equivalent | Unavailable in the stock profile |
| `Robot`, global pointer inspection, `SystemTray`, `TrayIcon`, `Taskbar`, native display-mode changes and global screen capture | No browser equivalent | Unavailable in the stock profile |
| File dialogs and printing | Excluded by scope | Not planned |

## Architecture

The public `java.awt` API will be separated from the browser implementation by narrow internal ports.

```text
java.awt public API
        |
org.webawt.internal model
        |
browser ports and peers
        |
Elemental2 DOM, Canvas, CSS and events
```

Public AWT classes must not expose Elemental2 or JavaScript types. Standard controls will use semantic HTML elements for native input behavior and accessibility. Layout managers will calculate bounds in Java, and DOM peers will apply those bounds using CSS. Custom painting will use Canvas 2D. Top-level windows will be layers within a single WebAWT application root.

The browser boundary will be divided into small interfaces such as `DomPeer`, `CanvasPeer`, `BrowserScheduler`, `BrowserEvents`, `BrowserImages`, `BrowserFonts`, `BrowserClipboard`, and `BrowserWindowing`. Production implementations will use Elemental2, while JVM-side tests will use deterministic fakes.

Reflection, `ServiceLoader`, classpath provider discovery and native peer lookup will be replaced by explicit factories or generated registries. Browser event listeners and resources must have explicit attach and disposal lifecycles.

Where a useful browser operation is necessarily asynchronous but its AWT counterpart is synchronous, the AWT behavior will remain deterministic and an optional asynchronous WebAWT extension will be placed outside `java.awt`.

## Dependencies and build

The primary build will use Bazel with Bzlmod and a pinned J2CL toolchain.

- Pin J2CL `20260402` and a compatible Bazel 8 release of at least 8.3.1.
- Pin stable Elemental2 `1.3.2`.
- Use `@elemental2//:elemental2-dom-j2cl` as the initial browser dependency.
- Do not add Guava, a UI framework, SVG, WebGL, media, IndexedDB or web storage to the initial implementation.
- Add a tiny project-owned JsInterop binding when a required browser API is missing from the pinned Elemental2 release instead of introducing another wrapper library.
- Keep build and test dependencies distinct from code shipped to consumers.
- Commit dependency locks and checksums and maintain license notices and a software bill of materials.

J2CL's open-source workflow is not supported directly on Windows. Local builds will therefore run under WSL2, and continuous integration will use Linux.

## Licensing and provenance

Original WebAWT code should use Apache-2.0 unless the project owner selects another permissive license before publication.

OpenJDK public documentation, signatures and black-box behavior may be used as the compatibility contract. OpenJDK implementation bodies and tests must not be copied because they are generally GPLv2 with the Classpath Exception, which does not make copied library code permissively licensed.

Apache Harmony contains Apache-2.0 AWT sources, but it is retired, targets an old Java release and contains desktop-native assumptions. It may only be used after a per-file provenance audit and is not the architectural base. The initial implementation will prefer original code.

Implementation agents will receive public API contracts and differential expected results rather than OpenJDK method bodies. Every reused algorithm or file must have an explicit provenance record. A legal review is required before public distribution.

## Coding and quality rules

- Disable automatic line wrapping and line-length rejection.
- Do not insert blank lines inside method bodies.
- Do not use wildcard imports.
- Do not use a formatter that rewrites long statements; Google Java Format is not suitable for this project.
- Prefer small single-purpose methods, descriptive names, low nesting, explicit contracts and narrow platform interfaces.
- Do not swallow exceptions, leave empty catch blocks, duplicate browser logic, or create uncontrolled mutable global state.
- Implement consistent `equals`, `hashCode`, and serialization identifiers where the public contract requires them.
- Give every browser listener and resource a defined disposal path.
- Apply a SonarQube quality gate to new code with no new issues and no more than 3 percent duplication. Enforce at least 80 percent coverage once optimized J2CL execution can be attributed to the original WebAWT Java sources without counting the OpenJDK differential reference implementation.
- Use Checkstyle or a small structural checker for formatting requirements that SonarQube does not enforce.
- Keep J2CL runtime checks at `NORMAL` and class metadata at `SIMPLE` until compatibility is established.

## Test strategy

### API and build conformance

Generate a machine-readable manifest of public classes, constructors, fields and methods for the selected OpenJDK baseline. Validate every referenced type and method against the pinned J2CL JRE. Classify dependencies as stock J2CL, implementable in an unclaimed package, requiring a J2CL patch, browser-limited, or excluded.

Compile the replacement package only in J2CL targets. JVM applications will use stock AWT; J2CL applications will use WebAWT. Identical WebAWT sources must not be transpiled by multiple J2CL library targets in the same bundle.

### Differential behavior

Run identical public test vectors against stock OpenJDK AWT on the JVM and WebAWT in a browser. Compare normalized JSON results for geometry, colors, transforms, layout bounds, event metadata and other portable behavior.

Explicitly test array boundaries and numeric corner cases because J2CL has different array-bound and floating-point behavior from a JVM.

### Unit and browser integration

- Test geometry, layout, component state, event dispatch and rendering command generation with deterministic fake ports.
- Use J2CL JUnit tests against a real DOM and Canvas implementation for mounting, disposal, focus, listener ordering, pointer translation, high-DPI handling, image loading and optimized Closure output.
- Record Canvas commands for most graphics tests so correctness does not depend on browser antialiasing.
- Use fixed bundled fonts and per-browser baselines with documented tolerances for selected visual tests.
- Verify semantic elements, accessible names, roles, disabled state, focus order and keyboard operation.
- Exercise clipboard, drag-and-drop and other gesture-sensitive features using dedicated browser integration scenarios.
- Use a single test-only cross-browser runner such as Playwright for Chromium, Firefox and WebKit if automated cross-browser acceptance is approved.
- Run SonarQube and style checks together with API, JVM differential, J2CL browser, optimized-output and accessibility gates.

### Phase 5: hardening and expansion

Expand supported raster, image and font behavior, validate real consumer applications, measure optimized bundle sizes, complete browser compatibility reports and add later Java API elements only when they can be implemented honestly.

## Agent execution model

The work will use one lead and at most three concurrent agents.

- The lead owns architecture decisions, shared build files, compatibility-manifest schema and final integration.
- A compatibility agent owns OpenJDK signature inventory and J2CL dependency auditing.
- An implementation agent owns one disjoint package or platform slice at a time.
- A test agent owns differential vectors, fake ports, browser tests and acceptance fixtures.

Agents will not edit shared files concurrently. Work will be divided into small dependency-ordered slices. Geometry and value types, events, layouts, browser peers, graphics, images and constrained integrations will have separate ownership.

For each slice, the compatibility agent defines the contract and browser mapping, the implementation agent writes production code and unit tests, a different agent reviews API parity and platform behavior, and the lead runs all build and quality gates. A slice is complete only when the compatibility manifest, implementation, tests, documentation, optimized build and quality results agree.

02A throwing body still has a signature

    throw new UnsupportedOperationException("Stub!");

The method does no file or network work. But the compiler must still resolve java.net.URI to check the declaration. The same applies to parameter types, return types, superclasses, interfaces, and declared exceptions throughout NIO.

The package you generate is NIO. The set of types needed to compile it is larger. Those external type declarations do not automatically become JavaScript output.

04Why this build contains a filter

I chose to copy a broad set of JDK classes as the starting reference library. That library contains both useful missing types and types J2CL already supplies. The filtering is a consequence of that choice.

The filter removes overlapping definitions so the build uses J2CL's versions of core types. Then ijar removes method bodies and other entries unnecessary for the resulting compile-time API.

05What is necessary, and what is a design choice?

See the measured dependency list: 19 extra JDK declarations suffice for the current NIO compilation.

Necessary for compilation

The compiler must have compatible declarations for all types referred to by the NIO API. Making every method throw does not remove that requirement.

A choice in this trial

Copying thousands of JDK classes and filtering them is one way to provide those declarations. A curated, compatible declaration JAR could replace this preparation step. That alternative has not been implemented here.

Your intuition about generation is correct: take the NIO API and generate throwing stubs. The extra machinery exists to make those stubs compile with J2CL's particular Java environment.

Compiling a library is a separate boundary from running an application. This archive is not a linked browser application. A consumer still needs a compatible runtime and must resolve overlapping NIO types when linking. Compile-time headers do not provide runtime implementations.

The remaining points of confusion

Does J2CL already include java.nio?

The pinned J2CL version 20260402 includes four top-level classes in java.nio.charset: Charset, IllegalCharsetNameException, StandardCharsets, and UnsupportedCharsetException. Its headers also contain one nested Charset class.

Your four generated versions are still transpilation inputs. The filter does not replace them with J2CL implementations.

Is the NIO check inside filter_api.py redundant?

Yes, for the current pipeline. generate.py already excludes java/nio/ and module-info.class from the cached reference JAR. The checks in filter_api.py are defensive. They remove zero additional entries in the current input.

Why not give J2CL the original JDK JAR unchanged?

It contains overlapping core definitions, and desktop JDK declarations are not interchangeable with J2CL's core declarations and compiler-specific helpers. The filter keeps J2CL's definitions authoritative. Stripping bodies is a separate concern: it makes the extra JAR an explicit compile-time API artifact.

Merely placing bytecode on a classpath does not itself transpile it. The source list controls what this build emits.

Why did CharArrayReader appear before?

The earlier build reused external implementation sources. The current build does not. The cached JDK reference JAR may contain CharArrayReader.class, and the extra header JAR can contain its declaration. Neither makes it a NIO source input or an output JavaScript class.

Which files implement these steps?
  • generate.py: writes and validates the NIO stubs; also saves the broad JDK reference JAR.
  • filter_api.py: removes overlap and invokes ijar.
  • compile_api.bzl: exposes J2CL's core compile-time JARs.
  • transpile.py: passes the NIO source list and reference declarations to J2CL.
  • BUILD.bazel: connects the build steps.
  • check_output.py: verifies package boundaries, source identity, and type coverage.
